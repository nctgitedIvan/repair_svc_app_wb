## 4. 設計要點

### 4.1 API 層：讓 UI 在 P5 之前可開發

```
pages/*  →  services/api/index.js  →  ┌─ _fake/  ← P7a 用這個
                                      └─ real/   ← P7b 實作
```

**`services/api/index.js` 的契約**（P7a 只實作 fake 這一側）：

```js
export async function getMyRole() { /* → { role, status } */ }
export async function fetchServices(params) {}
export async function fetchServiceDetail(serviceId) {}
export async function fetchMyOrders(params) {}
export async function fetchOrderDetail(orderNo) {}
export async function fetchTechnicianTasks(params) {}
export async function fetchTechnicianEarnings(params) {}
export async function fetchCsWorkbench(params) {}
export async function fetchWorkOrders(params) {}
```

### 4.2 ⚠️ 前端不能 import `packages/`

P0 的 F1 修正把 `packages/` 放進 `packOptions.ignore`，避免 domain 原始碼進前端 bundle。

**後果**：fake 的資料形狀必須**自己維護**，無法共用 domain 的型別。

| 風險 | 對策 |
|---|---|
| fake 與真實 DTO 走鐘 | ① 形狀以 `docs/01` 的 DTO 規格為準 ② P7b 的端到端測試會抓 ③ `check-frontend.js` 擋下任何 `packages/` 的 import（讓走鐘不會變成「偷偷共用」） |

### 4.3 Fake 資料刻意「過度完整」

`_fake/data.js` 的師傅端任務**刻意帶完整客戶姓名、手機、門牌**。

**目的**：讓「師傅端不顯示敏感資料」變成**可目視驗收**的事實 —— 若 UI 不小心渲染出來，一眼就看得到。若 fake 只給脫敏資料，這個測試就沒有意義。

### 4.4 Feature Flag（頁面層級，Q3 決策）

```js
// config/index.js
export const config = {
  useMock: true,
  /** 維修模式：true = 新介面；false = 原電商介面 */
  repairMode: true,
  /** API 來源：'fake'（P7a）| 'cloud'（P7b） */
  apiMode: 'fake',
};
```

**只允許在頁面的 `onLoad`／渲染入口判斷一次**，不得散佈到 `components/`／`services/`。
`check-frontend.js` 會限制 `repairMode` 只出現在 `pages/**/index.js`。
