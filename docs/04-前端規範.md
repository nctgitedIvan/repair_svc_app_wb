# 04 - 前端規範

> 適用範圍：`pages/`、`components/`、`custom-tab-bar/`、`services/`、`utils/`
> 建立日期：2026-10-16（P7a-1）
> 後端規範見 `docs/03-開發規範.md`

---

## 0. 最重要的一件事

> **把前端全刪掉，系統仍必須安全。**

若某條規則「刪掉前端就失效」，那條規則寫錯地方了 —— 它應該在後端的 `AccessPolicy`。

前端的職責是**體驗**，不是**安全**。兩者混淆會產生「看起來有防護、實際上沒有」的假象。

**這條規則由 `npm run check:frontend` 機械化保證**（見 §5）。

## 1. 五條紅線

| # | 紅線 | 為什麼 | 誰擋 |
|---|---|---|---|
| 1 | **不得判斷權限** | 前端不可信；權限只能由後端 `AccessPolicy` 決定 | `check:frontend` 規則 3 |
| 2 | **不得引用 `packages/` 或 `@repair/*`** | domain 不得進前端 bundle（撐大體積 + 洩漏領域邏輯） | `check:frontend` 規則 2 |
| 3 | **`wx.makePhoneCall` 必須登記在白名單** | 撥號本身不是問題，**撥給客戶**才是 | `check:frontend` 規則 1 |
| 4 | **`repairMode` 只允許在 `pages/` 底下** | 否則前端會布滿 `if (flag)` | `check:frontend` 規則 4 |
| 5 | **頁面只能透過 `services/api/index.js` 取資料** | 換實作（fake→cloud）時 UI 不用改 | `check:frontend` 規則 2 |

## 2. 角色處理：顯示 vs 權限

### 2.1 允許的用法

```js
// ✅ 依角色決定「顯示什麼」
import { isTechnician } from '../../utils/roleVisibility';
if (isTechnician(role)) {
  this.setData({ showEarnings: true });
}
```

### 2.2 禁止的用法

```js
// ❌ 依角色決定「能不能送出」—— 那由後端擋
if (canBool(actor, 'orders.accept')) {
  await acceptOrder();   // 前端就算不檢查，後端也會拒絕；檢查只是多餘
}
```

### 2.3 `utils/roleVisibility.js` 的定位

**它不是權限系統。** 它只提供角色判定與項目過濾，讓使用者不會看到不屬於他的介面。

- ✅ 可以用來：決定 tabBar 項目、隱藏不相關的按鈕、決定載入哪一份資料
- ❌ 不得用來：當作「後端也會同意」的前提

## 3. 師傅端資料可見範圍

**這是本專案最敏感的規則**（`docs/01` §3.4、A2、Q12）。

| 資料 | 師傅看到什麼 |
|---|---|
| 客戶姓名 | **只有姓氏**（王小明 → 王） |
| 客戶手機 | **`138****5678`**，永不例外 |
| 服務地址 | 接單後＝**區域 + 街道**；**服務當日 08:00 起**＝完整；完工後 7 天降級 |
| 平台抽成／分潤比例 | **看不到**（Q-E：比例是談判籌碼，公開會讓師傅互相比較） |
| 其他師傅的報酬 | 看不到 |

### 3.1 聯絡客戶的唯一方式

**沒有任何直接撥號的路徑。** 只有兩條通道（`docs/01` §6.4）：

| 通道 | 師傅拿到的號碼 |
|---|---|
| AXB 虛擬號 | **中間號**（雙方互不見號碼） |
| 客服三方通話 | **客服的號碼** |
| 兩者都不可用 | **拒絕**，提示改用客服工單 |

> 若通道都不可用，**不得退化為提供客戶號碼** —— 那等於繞過整個設計。

### 3.2 為什麼要讓 fake 資料「過度完整」

`services/api/_fake/data.js` 的師傅端任務**刻意帶完整姓名、手機、門牌**。

若 fake 只放脫敏資料，「師傅端不顯示敏感資料」的驗收會變成
**「UI 就算直接印出 `customer.phone` 也看不出問題」**。

**P7b 接上真實後端後，後端本來就只回脫敏資料**；這裡的「過度完整」是**前端端的壓力測試**。

## 4. 資料存取

```
pages/*  →  services/api/index.js  →  ┌─ _fake/  （P7a：記憶體假資料）
                                      └─ real/   （P7b：呼叫雲函數）
```

### 4.1 規則

- ✅ 頁面 `import { fetchServices } from '../../services/api/index'`
- ❌ 頁面 `import ... from '../../services/api/_fake'` 或 `.../real`

**理由**：P7b 換實作時（`config.apiMode` 從 `'fake'` 改 `'cloud'`），**UI 完全不用改**。

### 4.2 ⚠️ 為什麼前端不能共用 domain 的型別

`project.config.json` 的 `packOptions.ignore` 排除了 `packages/` —— 這是刻意的
（避免 domain 原始碼進前端 bundle）。

**代價**：view model 必須自己維護，有走鐘風險。
**對策**：P7b 的端到端測試會抓；`check:frontend` 擋下任何「偷偷 import packages」的企圖。

## 5. `check:frontend` 的規則

```bash
npm run check:frontend    # 併入 npm run verify
```

| 規則 | 內容 |
|---|---|
| 1 | `wx.makePhoneCall` 必須在 `PHONE_CALL_ALLOWLIST`（師傅端一律禁止，連白名單也無效） |
| 2 | 不得引用 `packages/`、`@repair/*`、`services/api/real`、`services/api/_fake` |
| 3 | `pages/` 不得出現 `AccessPolicy`、`canBool(`、`allowedPermissions(`、`RolePermissionMatrix` |
| 4 | `repairMode` 只允許在 `pages/` 底下 |

### 5.1 為什麼撥號用白名單而非全面禁止

撥號本身不是問題，**撥給客戶**才是。全面禁止會擋掉「客戶打給客服」的合理需求 ——
**那種規則最後一定會被繞過或放寬**。

白名單強迫每次新增撥號都必須**明示意圖**並登錄於 `scripts/check-frontend.js`：

```js
const PHONE_CALL_ALLOWLIST = {
  'pages/usercenter/index.js': '客戶主動撥打平台客服電話（非客戶號碼，非師傅端）',
  ...
};
```

### 5.2 檢查器本身也有測試

`tests/unit/frontend/checkFrontend.test.js` 有 18 項負向測試，每條規則都驗證「故意違反會被擋」。

核心邏輯是**純函式 `checkSource(relPath, source)`**，因此測試**不需要改動真實檔案**。

> 沿用 P0 的教訓：**只證明「乾淨的程式碼能通過」沒有意義。**

## 6. 微信平台限制（實測後確認，非猜測）

| # | 限制 | 影響 |
|---|---|---|
| 1 | **`tabBar.list` 上限 5 項** | 客戶 4 + 師傅 1 + 客服 1 = 6 → 超出。故 tabBar 只服務客戶端 |
| 2 | **tabBar 頁面必須在主包** | 訂單列表在分包 → 需另建主包 `pages/orders/index` |
| 3 | **分包頁面無法 `switchTab`** | 師傅／客服端用 `wx.reLaunch` + 自製底部導覽 |

### 6.1 tabBar 與角色的關係

`custom-tab-bar` **只服務客戶端**（首頁／服務／訂單／我的）。
師傅／客服／管理員由 `utils/roleRouter` 以 `wx.reLaunch` 導向各自工作台。

**`custom-tab-bar` 不做任何角色判斷** —— tabBar 是導覽元件，不是權限邊界。

## 7. Feature Flag

```js
// config/index.js
export const config = {
  repairMode: true,   // true = 維修介面；false = 原電商介面
  apiMode: 'fake',    // 'fake'（P7a）| 'cloud'（P7b）
};
```

| 允許 | 禁止 |
|---|---|
| 在 `pages/` 底下的檔案判斷 `repairMode` | 在 `components/`／`services/`／`utils/`／`custom-tab-bar/` 判斷 |

**理由**：改造期間任何一頁改壞了可以**單獨切回舊行為**，不必整包回滾。
但一旦散佈到元件層，前端就會布滿 `if (flag)` —— 那是不可維護的。

## 8. 常見錯誤

| 症狀 | 原因 | 解法 |
|---|---|---|
| `check:frontend` 說撥號未登記 | 新增了 `wx.makePhoneCall` | 確認對象不是客戶，再登錄白名單並寫理由 |
| `check:frontend` 說 repairMode 越界 | 在元件／服務裡用了 flag | 把判斷移到頁面層 |
| 頁面載入失敗、console 有 `[roleRouter]` 警告 | 目標頁尚未建立（P7a-2） | 正常，P7a-2 建頁面後即消失 |
| tabBar 高亮錯位 | 頁面不在 tabBar 清單中 | `init()` 會回傳 -1（全不亮），這是刻意的 |
| 編譯失敗：tabBar 指向不存在的頁面 | 改了 `app.json` 但頁面還沒建 | **先建頁面再改 `app.json`** |
