## 1. 🔴 我在寫 P2 計畫時發現的結構性問題（需你先決策）

### 1.1 問題：P2 的 Repository 契約依賴 P4 的聚合形狀，但 P2 排在 P4 之前

P0 的 `OrderRepository` 是**為了驗證管線而寫的佔位形狀**：

```js
// P0 的假設（packages/ports/OrderRepository.js 的註解 + InMemoryOrderRepository）
order = { id, orderNo, statusValue, serviceFeeCents, materialFeeCents,
          createdAt, version, snapshot: { profitSharingTerms } }
```

但 P4 會定義**真正的 `Order` 聚合**（`docs/01` §3.2）：

```js
Order {
  orderId, orderNo, status: OrderStatus,     // ← 值物件，不是 statusValue 數字
  amounts: { serviceFee: Money, ... },       // ← Money 值物件，不是 cents 數字
  items: OrderItem[], timeline: OrderStatusLog[], appointmentAt, ...
}
```

**後果**：若 P2 照原順序寫 `CloudDBOrderRepository`，它會在 P4/P5 被**打掉重寫** —— 包括 port 契約、CloudDB 實作、in-memory 替身、契約測試。而 `OrderQueryPort` 的角色化脫敏方法（§4.7.7）更是完全依賴聚合形狀。

這是你要求的「檢查是否有類似缺口」在 P2 的對應版本。

### 1.2 兩個選項

| | (a) **調整順序：P1 → P4 → P2 → P3 → P5**（建議） | (b) 維持原順序 |
|---|---|---|
| 做法 | P4（domain 核心）提前；P2 之後對著**真實聚合**寫 Repository | P2 只寫「簡單讀模型」的 Repository；聚合型的延到 P4 之後 |
| 優點 | 一次做對，零重寫。且 P4 零外部依賴，現在就能做 | 不動既有階段編號 |
| 缺點 | 階段編號變動；雲端資源（集合）稍晚建立 | **聚合類 Repository 仍要重寫一次**（P0 的 `OrderRepository` + in-memory + 契約測試） |
| 依賴檢查 | P4→P1 ✓；P2→P1,P4 ✓；P3→P2,P4 ✓；P5→P3,P4 ✓ | 同前，但 P2 範圍縮小 |

**我的建議是 (a)。** 理由：P2 的主要價值是「把持久化做對」，而「對」的定義取決於聚合形狀。在形狀未定前寫持久化，等於保證重工。P4 零外部依賴、可離線測試，提前做的成本極低。

> **本計畫以下內容以 (a) 為前提**。若你選 (b)，差異見 §9。

**做法**：抽出一組「契約測試」函式，對兩份實作跑同一套斷言。
