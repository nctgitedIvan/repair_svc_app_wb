## 1. 🔴 我在寫 P2 計畫時發現的結構性問題（需你先決策）

### 1.1 問題：P2 的 Repository 契約依賴 P4 的聚合形狀，但 P2 排在 P4 之前

P0 的 `OrderRepository` 是**為了驗證管線而寫的佔位形狀**：

```js
// P0 的假設（packages/ports/OrderRepository.js 的註解 + InMemoryOrderRepository）
order = { id, orderNo, statusValue, serviceFeeCents, materialFeeCents,
          createdAt, version, snapshot: { profitSharingTerms } }
```

但 P4 會定義**真正的 `Order` 聚合**（`docs/01` §3.2）：

```js
Order {
  orderId, orderNo, status: OrderStatus,     // ← 值物件，不是 statusValue 數字
  amounts: { serviceFee: Money, ... },       // ← Money 值物件，不是 cents 數字
  items: OrderItem[], timeline: OrderStatusLog[], appointmentAt, ...
}
```

**後果**：若 P2 照原順序寫 `CloudDBOrderRepository`，它會在 P4/P5 被**打掉重寫** —— 包括 port 契約、CloudDB 實作、in-memory 替身、契約測試。而 `OrderQueryPort` 的角色化脫敏方法（§4.7.7）更是完全依賴聚合形狀。

這是你要求的「檢查是否有類似缺口」在 P2 的對應版本。

### 1.2 兩個選項

| | (a) **調整順序：P1 → P4 → P2 → P3 → P5**（建議） | (b) 維持原順序 |
|---|---|---|
| 做法 | P4（domain 核心）提前；P2 之後對著**真實聚合**寫 Repository | P2 只寫「簡單讀模型」的 Repository；聚合型的延到 P4 之後 |
| 優點 | 一次做對，零重寫。且 P4 零外部依賴，現在就能做 | 不動既有階段編號 |
| 缺點 | 階段編號變動；雲端資源（集合）稍晚建立 | **聚合類 Repository 仍要重寫一次**（P0 的 `OrderRepository` + in-memory + 契約測試） |
| 依賴檢查 | P4→P1 ✓；P2→P1,P4 ✓；P3→P2,P4 ✓；P5→P3,P4 ✓ | 同前，但 P2 範圍縮小 |

**我的建議是 (a)。** 理由：P2 的主要價值是「把持久化做對」，而「對」的定義取決於聚合形狀。在形狀未定前寫持久化，等於保證重工。P4 零外部依賴、可離線測試，提前做的成本極低。

> **本計畫以下內容以 (a) 為前提**。若你選 (b)，差異見 §9。

**做法**：抽出一組「契約測試」函式，對兩份實作跑同一套斷言。

## 12. 企業級補強（§A／§B／§C）

> 你要求新增的三節。**它們橫跨 P1–P6，不只落在 P2**，因此每節都標明階段歸屬。
> 每節都先列出「與現行設計的衝突或做不到的地方」——這些比設計本身更重要。

### 12.A 審計日誌的不可篡改性

#### A-1 ⚠️ 先講一個做不到的要求

| 你的要求 | 可行性 | 說明 |
|---|---|---|
| **DB 權限層**強制「只允許 insert，禁止 update/delete」 | 🔴 **做不到** | 微信雲開發的資料庫權限是**集合級「讀／寫」**，**無法細分到操作類型**。設為「僅管理端可讀寫」後，管理端仍可 update / delete |

**替代方案（三層防護）**：

| 層 | 機制 | 擋什麼 |
|---|---|---|
| 1 | `AuditLogRepository` **只暴露 `append()`**，無 update / delete 方法 | 應用層無法誤用 |
| 2 | `check-layering` 新規則：**只有** `audit_logs` 的 adapter 可碰該集合 | 其他 adapter 無法繞過 |
| 3 | **哈希鏈** | 即使有人直接改 DB，**篡改必被偵測** |

**誠實的降級**：從「不可能篡改」變成「篡改必被發現」。在雲開發的權限模型下，這已是上限。

#### A-2 哈希鏈設計

| # | 路徑 | 職責 | 階段 |
|---|---|---|---|
| A-1 | `packages/domain/audit/AuditChain.js` | `computeHash(prevHash, entry)`；`verifyChain(entries)` | **P4** |
| A-2 | `packages/adapters/clouddb/CloudDBAuditLogRepository.js` | append 時讀尾、計算、寫入 | **P2b** |
| A-3 | `cloudfunctions/*`（定時任務） | 每日驗證全鏈 | **P6** |

```
hash = sha256( prevHash + canonicalJSON(entry) )

canonicalJSON：鍵依字典序排序、無多餘空白、數字不轉字串
（若不做正規化，同一筆資料在不同 JS 引擎可能算出不同 hash）
```

**每筆記錄欄位**：`prevHash`、`hash`、`seq`、`chainId`。

#### A-3 ⚠️ 哈希鏈的併發問題（必須先解）

`prevHash` 依賴前一筆 → **並發 append 會讓鏈分叉**。

| 對策 | 說明 | 代價 |
|---|---|---|
| **分段鏈（建議）** | 每訂單一條鏈（`chainId = order:xxx`）+ 每日一條全域鏈 | 無需全域序列化；審計查詢天然是按訂單或按期間 |
| 單一全域序列 | 用 `id_sequences` 取序號，全域序列化 | 熱點，高併發下成為瓶頸 |
| 樂觀鎖重試 | 讀尾 → 算 → 條件寫入，衝突重試 | 高併發下重試風暴 |

**建議採分段鏈。**

#### A-4 斷點處理

- 驗證失敗 → 寫入**新集合 `audit_integrity_alerts`**（含 `chainId`、`brokenAtSeq`、偵測時間）
- 通知管理員（走 `NotificationPort`）
- **告警本身也要寫稽核**（否則「掩蓋告警」成為新的攻擊面）

#### A-5 效能代價（誠實提醒）

每筆稽核多一次「讀尾」+ 一次 sha256。稽核量大時這會是瓶頸。
**P2 先用最簡單的做法，P5 量測後再優化**（批次寫入／鏈尾快取）。不預先優化。

### 12.C 可追溯性與職責分離

#### C-1 traceId 全程攜帶

| # | 內容 | 階段 |
|---|---|---|
| C-1a | 入口產生 UUID v4（用 Node 內建 `crypto.randomUUID()`，**不需外部套件**） | **P3** |
| C-1b | `entrypoint-kit` 新增 `withTrace()`；`toResponse` 回傳 `traceId` 供前端回報問題 | **P3** |
| C-1c | traceId 寫入 `audit_logs`、logger meta、所有 `*_records` | **P3 / P5** |

⚠️ **這是 P1 既有代碼的改動**（`createHandler.js`、`toResponse.js`），不是純新增。

> **為什麼 traceId 在入口產生而非 domain**：domain 禁止 `Math.random()` / `crypto`（非確定性）。
> 入口產生、以參數往下傳 —— 與 `now` 的處理方式一致。

#### C-2 職責分離（SoD）：發起者不得批准

| 機制 | 說明 |
|---|---|
| 記錄發起者 | `refund_records.requestedBy` |
| 規則 | `ApproveRefund*` 檢查 **`requestedBy !== actor.id`**，否則拋 `SoDViolationError` |
| 錯誤型別 | `SoDViolationError` 加入 `packages/shared-kernel/Errors.js` ⚠️ **P1 既有代碼改動** |
| 實作位置 | **P4**（`AccessPolicy` 的 SoD 規則）+ **P3**（wiring） |

⚠️ **與「≤200 元客服可自批」的衝突**：

> 若客服 A 代客戶發起退款、**又自己批准**（金額 ≤ 200），即違反 SoD。

**對策**：發起與批准必須是不同人。
**後果**：客服中心若只有一人，退款會卡住。**需你確認**（§13 Q6）。

#### C-3 敏感操作雙人覆核

| 操作 | 覆核者 | 階段 |
|---|---|---|
| 改分潤比例 | 兩個不同 admin | **P4**（`ApprovalPolicy`）+ **P8**（admin-api） |
| 改商品價超 20% | 兩個不同 admin | 同上 |
| **刪訂單** | admin + cs_agent | ⚠️ **見 C-4** |

- 新集合 **`approval_records`**（申請人、覆核人、目標、前後值、時間）
- 覆核必須來自**不同帳號**（比對 `userId`）

#### C-4 ⚠️「刪訂單」與現行設計衝突

> 你的要求寫「**刪訂單：admin + cs_agent**」，但：
> - `docs/01` §4.6 明文：**「業務資料一律軟刪除，任何角色皆不得硬刪除」**
> - 你在更早的回覆中確認過這條

**需要澄清**（§13 Q7）：此處的「刪訂單」是指
- (a) **軟刪除／作廢**（`status = 'voided'`，資料保留）→ 與現行設計相容，只是加雙人覆核
- (b) **硬刪除**（真的從資料庫移除）→ **與現行設計直接衝突**，且會破壞稽核鏈與對帳

**我目前按 (a) 理解並設計**，但需要你確認。

#### C-5 ⚠️ 雙人覆核的實務風險

**需要兩個 admin 同時在線。若只有一個 admin，所有改價與改分潤都會卡住。**

| 選項 | 說明 |
|---|---|
| (a) 嚴格雙人，無例外 | 最安全，但**單一 admin 時系統實質停擺** |
| (b) 緊急單人覆核 + 強制稽核 + 事後通知 | 可運作，但安全性取決於事後審查 |
| (c) 金額／幅度門檻 | 小額改動單人，大額雙人（與退款門檻同思路） |

**需你決定**（§13 Q8）。我沒有預設答案 —— 這取決於你的團隊規模。
