## 0. 最重要的一件事

**架構規則不是靠自律，是靠 `npm run check:layering` 機械化保證的。**

本文件描述的所有「不得」，都已經寫成 `scripts/check-layering.js` 的檢查。
若你的程式碼違規，**commit 前就會被擋下**（husky pre-commit），或至少 `npm run verify` 會紅。

> 規則若不能被腳本檢查，就只是願望。

## 1. 分層與依賴方向

### 1.1 六個共享套件

| 套件 | 職責 | 可依賴 |
|---|---|---|
| `@repair/shared-kernel` | `Money`、`Result`、錯誤型別 | **無**（零依賴） |
| `@repair/domain` | 實體、值物件、狀態機、領域策略 | `shared-kernel` |
| `@repair/ports` | 介面定義（無實作） | `shared-kernel`、`domain` |
| `@repair/application` | Use Case | `shared-kernel`、`domain`、`ports` |
| `@repair/entrypoint-kit` | 雲函數入口中介層 | `shared-kernel`、`ports` |
| `@repair/adapters` | Ports 的實作 | 不限（邊界層） |

依賴方向**單向向內**：

```
entrypoints → application → domain
                  ↓
                ports ← adapters（實作）
```

### 1.2 四條鐵律

| # | 規則 | 為什麼 |
|---|---|---|
| 1 | **domain 不碰外部世界** | 這是可測試性與可替換性的唯一保證 |
| 2 | **ports 只有介面，沒有實作** | 出現 `new` 就代表實作滲進了契約層 |
| 3 | **只有 `bootstrap.js` 可以 `new` adapter** | 組裝點唯一，測試才替換得掉 |
| 4 | **adapters 不判斷角色** | 角色規則只能有一個真實來源（domain 策略） |

## 2. domain 層禁止清單

`packages/domain/**` **不得出現**下列任何字串（CI 會擋）：

| 禁止 | 原因 |
|---|---|
| `wx-server-sdk` | 微信雲 SDK |
| `wx.cloud` | 小程序雲 API |
| `DYNAMIC_CURRENT_ENV` | 雲開發環境常數 |
| `cloud.database` / `cloud.callFunction` / `cloud.getWXContext` | 雲開發 API |
| `getWXContext` | 微信上下文 |
| `.collection(` / `db.collection` | 直接存取資料庫 |
| `Date.now(` | 非確定性時間 → **改用 `ClockPort`，以參數傳入** |
| `new Date()` | 同上 |
| `Math.random(` | 非確定性隨機 → **改用 `IdGeneratorPort`** |
| `process.env` | 環境變數只允許 adapter 讀 |
| `console.log/error/warn` | **改用 `LoggerPort`** |
| 任何非相對路徑且非 `@repair/shared-kernel` 的 `require`/`import` | domain 只能依賴自己與 shared-kernel |

### 2.1 ⚠️ 一個容易誤解的地方

`ClockPort` **不是** domain 的依賴。它住在 `packages/ports`，而 domain 的純函式
**以參數接收 `now`**：

```js
// ✅ 正確：domain 純函式，時間由呼叫方傳入
function discloseFor({ viewer, order, now, config }) { /* ... */ }

// ❌ 錯誤：domain 自己取時間，測試無法重現
function discloseFor({ viewer, order }) {
  const now = Date.now();
}
```

## 3. Use Case 規範

### 3.1 Constructor injection（強制）

```js
class AssignOrderUseCase {
  // ✅ 所有依賴由建構子注入
  constructor({ orderRepository, technicianRepository, unitOfWork, clock, logger }) {
    this.orderRepository = orderRepository;
    // ...
  }
  static get allowedRoles() { return ['cs_agent', 'admin']; }
}
```

**Use Case 內不得出現 `new`**（`Result`、值物件等無依賴物件除外）。
`new` 一個有依賴的物件，就等於把依賴藏起來，測試無法替換。

### 3.2 回傳 DTO，不回傳實體

```js
// ✅
return Result.ok({ orderId: order.id, status: order.status.key });

// ❌ 只要有一個 Use Case 破了這條，AddressView / MaskedPhone 的型別保證就全部失效
return Result.ok(order);
```

**判準**：回傳物件不得含 `snapshot`、`version`、內部欄位或客戶完整 PII。

### 3.3 三層校驗的位置

| 層 | 內容 | 寫在哪 |
|---|---|---|
| 1 身分 | openid 是否有效 | `entrypoint-kit/authenticate.js` |
| 2 角色 | 這個角色能否執行這類 Use Case | 入口的 `allowedRoles` 比對 |
| 3 **資源歸屬** | **這一筆**資料是否屬於他 | **Use Case 內**（不可放入口） |

> ⚠️ 第 2 層通過**不等於**第 3 層通過。「師傅可更新訂單」的真正意思是
> 「只能更新**被指派給自己**的那張單」。

## 4. Adapters 規範

### 4.1 只做翻譯，零業務規則

| 寫法 | 判定 |
|---|---|
| 呼叫 `AddressDisclosurePolicy.discloseFor(...)` | ✅ 允許（這是投影／翻譯） |
| `Order.rehydrate(row)` | ✅ 允許（domain-aware 翻譯） |
| `if (viewer.role === 'technician') address.slice(...)` | ❌ **違規**（規則被複製到 adapter，會與 domain 走鐘） |
| `const commission = total * 0.8` | ❌ 違規（金額計算屬 domain） |
| `if (order.paid) status = ASSIGNED` | ❌ 違規（狀態流轉屬 domain） |

**判準**：把 adapter 換成 in-memory fake，**業務行為必須完全不變**。若會變，就是漏了。

### 4.2 角色判斷由 CI 擋下

偵測正則 `/\.role\s*[!=]==?/` —— 只抓**比較**，不抓物件字面量：

```js
{ viewer: { role: 'technician' }, order }   // ✅ 合法傳參
viewer.role === 'technician'                 // ❌ 違規
```

## 5. 雲函數入口規範

### 5.1 只做四件事

```js
exports.main = async (event) => {
  try {
    const input = validate(event, SCHEMA);                          // ① 參數校驗
    const auth = await authenticate(cloud.getWXContext(), container); // ② 身分驗證
    if (!auth.ok) return toResponse(auth);
    if (!UseCase.allowedRoles.includes(auth.value.role)) return toResponse.forbidden();
    const useCase = new UseCase(container);                          // ③ 呼叫 use case
    return toResponse(await useCase.execute({ actor: auth.value, ...input.value })); // ④
  } catch (err) {
    return toResponse.error(err, container.logger);
  }
};
```

或直接用 factory 減少樣板：

```js
exports.main = createHandler({
  schema: SCHEMA, UseCase, container,
  getWxContext: () => cloud.getWXContext(),
  logger: container.logger,
});
```

### 5.2 禁止出現在 `index.js` 的東西

`if` 判斷訂單狀態、金額加減、`for` 迴圈處理業務資料、`db.collection(...)`。

**建議上限：60 行。**

### 5.3 為什麼每個雲函數各有一份 `bootstrap.js`

這是**刻意的重複**。每個部署單元自己決定依賴，正是 composition root 的意義；
共用會把組裝邏輯塞進 `entrypoint-kit`，反而破壞「只有 bootstrap 可以 new adapter」。

走鐘風險由 `tests/unit/composition/containerContract.test.js` 守住：
四支的依賴鍵若不一致，測試會紅。

## 6. 共享碼同步

### 6.1 日常工作流

```bash
# 改了 packages/ 之後
npm run sync          # 複製到各雲函數的 node_modules
npm run sync:check    # 驗證是否同步
```

### 6.2 三道防線

| 時機 | 機制 | 防的是什麼 |
|---|---|---|
| commit 前 | husky `pre-commit` | 忘記同步就 commit |
| 部署前 | `npm run predeploy` | 同上 |
| 執行期 | `assertSharedBuild()` | 部署時 node_modules 是舊的 |

**若雜湊不符，雲函數會拒絕啟動。** 這是刻意的——寧可整個函數掛掉，
也不要讓舊版 domain 規則（例如沒有 `DISPUTED` 凍結規則）靜默地處理金流。

### 6.3 開發用連結

`sync-shared.js` 也會在專案根目錄建立 `node_modules/@repair/*` → `packages/*` 的目錄連結，
讓本地測試與 IDE 能解析 `require('@repair/domain')`。

> `npm install` 會清除這些「多餘」目錄，因此 `package.json` 有 `postinstall` 自動重建。

## 7. 部署 SOP

### 7.1 ⚠️ 必須選擇「上傳所有檔案（含 node_modules）」

**不可選「雲端安裝依賴」。** 原因：

`@repair/*` **刻意不宣告為 `dependencies`**（若宣告為 `file:` 依賴，雲端安裝時會找不到目標而失敗）。
它們只以實體檔案存在於 `node_modules`，因此必須隨上傳一併帶上去。

若選「雲端安裝依賴」，npm 會清除這些「多餘」套件，函數啟動時就會因
`assertSharedBuild()` 失敗而拒絕服務。

### 7.2 部署步驟

```bash
npm run predeploy        # sync + sync:check + check:layering + test
```
再到微信開發者工具：右鍵雲函數 → **上傳並部署：上傳所有檔案（含 node_modules）**。

### 7.3 環境

| 環境 | 用途 |
|---|---|
| `repair-test` | 開發與測試。**金流測試只能在這裡跑** |
| `repair-prod` | 生產 |

環境 ID 寫在 **gitignored 的 `.env.local`**，不進版控。

## 8. Commit 規範

沿用既有的 conventional commits（`commitlint` 已設定）：

```
<type>: <描述>
```

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修錯 |
| `docs` | 文件 |
| `chore` | 雜項 |
| `refactor` | 重構 |
| `test` | 測試 |

### 8.1 兩條專案專屬規則

1. **新增檔案與修改既有檔案分開 commit。** 讓「只回滾改動、保留新增」成為可能。
2. **階段任務標註編號**，例如 `P1-T6: 拆分 config/areaData`。方便精準 revert。

## 9. 測試規範

### 9.1 執行

```bash
npm test              # 全部
npm run test:domain   # domain 專屬（必須能在離線環境跑）
npm run test:entrypoint
npm run test:security
npm run verify        # 依賴檢查 + 同步檢查 + 測試
```

### 9.2 要求

| 層 | 要求 |
|---|---|
| domain | **不得啟動任何雲端資源**；測試執行時間應在毫秒級 |
| application | 全程使用 in-memory fake |
| 安全 | 越權、DTO 洩漏必須有自動化斷言 |

### 9.3 ⚠️ 負向測試是必要的

**只證明「乾淨的程式碼能通過」沒有意義。** 每個新規則都要有對應的負向測試：
故意違反 → 確認被擋 → 移除。

P0／P1 已建立的負向測試涵蓋：domain 用 `Date.now()`、跨層依賴、
非 bootstrap 處 `new adapter`、改 `packages/` 未同步、雜湊篡改、
adapters 角色判斷。

## 11. 常見錯誤（給未來的自己）

| 症狀 | 原因 | 解法 |
|---|---|---|
| `Cannot find module '@repair/xxx'` | 沒跑 `npm run sync`，或 `npm install` 清掉了連結 | `npm run sync` |
| `[FATAL] 共享碼版本不符` | 改了 `packages/` 但沒同步就部署 | `npm run sync` 後重新部署 |
| 雲函數部署後啟動失敗 | 選了「雲端安裝依賴」 | 改用「上傳所有檔案」 |
| `check-layering` 說 adapters 有角色判斷 | 在 adapter 裡寫了 `role ===` | 改用 domain 策略 |
| 測試 `MODULE_NOT_FOUND` 但檔案存在 | 忘了同步開發連結 | `npm run sync` |
| `git commit` 被 husky 擋下 | 違反架構規則或測試失敗 | 依訊息修正，**不要用 `--no-verify` 繞過** |
