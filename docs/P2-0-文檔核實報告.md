## 1. 查核結果

### 1.1 事務（`db.startTransaction` / `db.runTransaction`）

| 項目 | 官方說法 |
|---|---|
| **是否支援** | ✅ **支援** |
| **環境限制** | **僅雲函數端**；需 `wx-server-sdk` **≥ 1.7.0** |
| **隔離級別** | **快照隔離（snapshot isolation）** |
| **⚠️ 隔離級別限制** | **不支援可序列化隔離 → 無法避免「寫偏」（write skew）** |
| **⚠️ 操作限制** | **只允許單記錄操作**：`collection.add` 與 `collection.doc().get/update/set/remove`。**不允許 `where` 批次操作與 `aggregate`** |
| 可跨集合 | ✅ 可以（同一事務內多次 doc 操作） |
| **⚠️ 次數限制** | **單一事務最多 100 次操作** |
| **⚠️ 時間限制** | **執行時間 ≤ 30 秒** |
| 衝突處理 | 事務鎖：其他事務的寫入**立即失敗**；一般更新被阻塞至鎖釋放或逾時 |
| 兩種介面 | `runTransaction`（自動重試衝突）／`startTransaction`（手動控制流程） |

**原文摘錄**：
> 「事务操作时为保障效率和并发性，**只允许进行单记录操作，不允许进行批量操作**，
>  但可以在一个事务进行多次数据库操作」

> 「在提交时，会将修改的快照原子性地写入数据库」

### 1.2 原子遞增（`db.command.inc`）

| 項目 | 官方說法 |
|---|---|
| **是否支援** | ✅ **支援，且明確標示為原子操作** |
| 語意 | 「**原子自增**字段值」；值可正可負 |
| 為何重要 | 「多个用户同时写入时，数据库会将其视为字段的自增，**不会出现后来的写入覆盖先前写入的情况**」 |
| 附帶好處 | 減少網路請求（不需先讀再寫回） |

## 2. 對本專案設計的影響

### 2.1 ✅ 三個原本掛心的場景都有解

| 場景 | 做法 | 為何可行 |
|---|---|---|
| **每日退款配額** | 事務內：`cs_agents.doc(id).get()` → 判斷 → `.update()` | 單一 doc，符合「單記錄操作」限制 |
| **商品庫存扣減** | `products.doc(id).update({ stock: _.inc(-1) })` | doc 操作 + `inc` 原子，**雙重保障** |
| **混合訂單**（扣庫存 + 建訂單） | 同一事務內：`orders.add()` + 多個 `products.doc().update()` | 可跨集合、可多次 doc 操作 |

**→ 「轉移能力探針」至此可以跳過。P2 直接按「支援事務與原子遞增」設計。**

### 2.2 ⚠️ 但文檔揭露了**兩個原本沒預期到的架構限制**

**(A) 事務內不能用 `where` → 影響定時任務的寫法**

`RecoverStuckSettlements`、`AutoExpireUnassignedOrders` 這類任務的直覺寫法是
「查出符合條件的多筆 → 批次更新」。這在事務內**做不到**。

**必須改為兩段式**：

```
第一段（事務外）：查出符合條件的 orderId 清單
第二段（逐筆、各自一個事務）：對每個 orderId 做 doc 操作
```

**這會寫進 P2 的契約測試與 P5 的定時任務設計。**
副作用：**批次處理不具原子性** —— 中途失敗會留下部分完成的狀態。
因此每筆都要**冪等**（重跑不會重複處理），這與我們既有的冪等鍵設計一致。

**(B) ⚠️ 快照隔離不防「寫偏」**

官方明說「目前只支援快照隔離，**無法避免寫偏**」。

**寫偏是什麼**：兩個事務各自讀取一組資料、各自寫入**不同**的記錄，
彼此沒有寫-寫衝突，因此都能提交 —— 但整體不變式被破壞。

**對我們的意義**：

| 場景 | 是否受寫偏影響 | 理由 |
|---|---|---|
| 每日配額 | ❌ 不受影響 | 兩個事務都寫**同一個** `cs_agents` doc → 有寫-寫衝突 → 事務鎖會擋下其一 |
| 庫存扣減 | ❌ 不受影響 | 同一 `products` doc |
| **跨 doc 的不變式** | ⚠️ **可能受影響** | 例如「訂單總額 = 各分帳紀錄之和」這種跨文件不變式 |

**目前的設計沒有跨 doc 不變式**，所以**沒有立即風險**。
但**必須記在案**：日後若新增「多筆記錄加總必須等於某值」這類規則，不能只靠事務。

### 2.3 建議：計數器一律「事務 + `_.inc()`」雙重保障

即使事務鎖已能防止同 doc 的競態，**計數器仍建議用 `_.inc()` 而非「讀-算-寫」**：

| 寫法 | 風險 |
|---|---|
| 讀 `usedCents` → 算新值 → 寫入 | 若事務實作有誤或未來降級，會丟更新 |
| `update({ usedCents: _.inc(amount) })` | **資料庫層保證原子**，不依賴事務語意 |

**代價**：無法在寫入前用 `_.inc()` 判斷「是否超額」——
所以需要「先在事務內讀取判斷 → 再用 `_.inc()` 寫入」的組合。

這點寫進 P2 的 `CloudDBUnitOfWork` 實作要點。
