## 3. 一項與計畫不同的決定：不用 Vitest，改用 `node:test`

`docs/02-實施計畫.md` 原本建議 **Vitest**。實作時改為 **Node 內建測試執行器**，理由：

| 面向 | Vitest | `node:test`（採用） |
|---|---|---|
| 依賴 | 需 `npm install`（數百 MB） | **零依賴** |
| 網路 | 需要 | **不需要** |
| 供應鏈風險 | 有 | **無** |
| domain 離線測試 | 可以，但要先裝 | **天生就是** |
| 執行速度 | 快 | 更快（本例 51 測試 **96ms**） |
| 覆蓋率報告 | 內建 | 需 `--experimental-test-coverage` |

**決定性理由**：你要求「domain 層能否在**完全不啟動微信雲環境**的情況下跑單元測試」。若測試框架本身需要 `npm install`，那「離線可測」就打了折扣。`node:test` 讓這個保證變成**結構性的**，而不是「裝完之後就可以」。

**代價**：無 watch 模式的開箱體驗、無內建覆蓋率 UI。若 P1 之後需要，可再加 Vitest 作為並行選項，不衝突。

> 環境：Node **v24.21.0**、npm 11.19.0（皆已具備 `node:test`）。

## 5. P0 過程中發現並修正的缺陷

> 這是 P0 真正的產出：**四個缺陷，其中三個會直接影響交付品質。**

### 5.1 【真實缺陷】`require('@repair/*')` 在 repo 根目錄無法解析

| 面向 | 內容 |
|---|---|
| **症狀** | `npm test` 直接 MODULE_NOT_FOUND：`Cannot find module '@repair/shared-kernel/Result'` |
| **原因** | 雲函數靠 sync 把共享碼複製進**自己的** `node_modules` 才能解析；但 repo 根目錄沒有 `node_modules/@repair`，本地測試與 IDE 分析全部失敗 |
| **為什麼嚴重** | 這會讓「domain 可離線測試」這個核心保證**從第一天就是假的**。而且它不是雲端問題，是本地開發的日常阻塞 |
| **修正** | `sync-shared.js` 額外建立 `node_modules/@repair/*` → `packages/*` 的**目錄連結**（Windows 用 junction，不需管理員權限）。並加 `postinstall` 自動重建（因為 `npm install` 會清除「多餘」目錄） |
| **為何用連結而非複製** | 避免出現第二份副本走鐘；本地永遠看到 `packages/` 的最新內容 |

### 5.2 【真實缺陷】狀態機的函式呼叫錯誤

| 面向 | 內容 |
|---|---|
| **症狀** | `TypeError: OrderStatus.fromValue is not a function` |
| **原因** | 我把 `fromValue` / `canExecuteProfitSharing` 寫成 enum 的方法（`OrderStatus.fromValue(...)`），但它們其實是模組層級的具名匯出 |
| **修正** | 改為獨立解構匯入。**已一併修正 `cloudfunctions/spike-hello/index.js` 的同類錯誤**（否則部署後才會炸） |
| **教訓** | 這正是「無 TypeScript」的代價（`docs/00` §8.3 R14）。若 P1 後考慮加 `.d.ts` 或 JSDoc 型別檢查，此類錯誤可在編輯期攔下 |

### 5.3 【設計缺陷】共享碼守衛只「定義」而沒有「執行」

| 面向 | 內容 |
|---|---|
| **症狀** | 負向測試 5（篡改雜湊後載入）**沒有擋下** |
| **原因** | `assertSharedBuild()` 只在 `bootstrap.js` 被**定義**並匯出，實際呼叫寫在 `index.js`。等於「守衛存在，但要不要站崗取決於入口記不記得」 |
| **為什麼嚴重** | 一個忘記呼叫的入口，就會用**舊版 domain 規則處理金流**——例如舊版沒有 `DISPUTED` 凍結規則，爭議中的訂單照樣分帳給師傅 |
| **修正** | 改為 `bootstrap.js` **模組載入即自我檢查**。任何 require 了 bootstrap 的檔案都會觸發；入口的顯式呼叫保留但變為冪等 |
| **驗證** | 見 §6 負向測試 5，現在會拋出明確錯誤 |

### 5.4 【我的測試寫錯】手機號偵測的偽陽性

| 面向 | 內容 |
|---|---|
| **症狀** | DTO 掃描測試失敗，但它其實是**誤報** |
| **原因** | 我用了 `/\d{11}/`。13 位時間戳（`1700000000000`）本身就含有 11 位數字子字串 |
| **修正** | 改用**手機號形狀**的正則 `/(?<!\d)1[3-9]\d{9}(?!\d)/`（1 開頭、次位 3-9、共 11 位、前後不接數字） |
| **為什麼要記錄** | 這個斷言是 P3「師傅端 DTO 不得洩漏客戶完整手機號」安全測試的雛形。**一個會誤報的安全測試，最後一定會被註解掉**——那就等於沒有 |

## 7. P0-2 的防禦設計（「雲端安裝依賴」風險）

**問題**：微信雲函數部署時有兩種模式。「雲端安裝依賴」會執行 `npm install`，而 npm 會**清除 node_modules 中不在 `dependencies` 裡的「多餘」套件**——我們的 `@repair/*` 正是這樣的存在。

**已採取的防禦**：`sync-shared.js` **刻意不把 `@repair/*` 宣告為 dependencies**。

| 若宣告為 dependencies | 已採取的做法 |
|---|---|
| 用 `file:./node_modules/...` → 雲端安裝時找不到目標，**install 直接失敗** | 完全不宣告。檔案實體存在於 `node_modules`，Node 可直接解析 |
| 「雲端安裝依賴」可能清除它們 | 但至少不會讓 install 失敗；且部署時必須選「上傳所有檔案」 |

**結論**：部署 `spike-hello` 時**必須選擇「上傳所有檔案（含 node_modules）」**，不可選「雲端安裝依賴」。此點需你在 §8 的步驟中實測確認。

## 8. ⏸ 需要你執行的部分（我無法代勞）

以下步驟需要微信開發者工具與你的雲開發環境。**這是 P0 的唯一缺口。**

### 步驟

1. **開啟專案**：用微信開發者工具開啟 `miniprogram-repair`，確認左側出現 `cloudfunctions` 目錄與 `spike-hello`（若沒有，檢查 `project.config.json` 的 `cloudfunctionRoot`）。
2. **部署**：右鍵 `spike-hello` → **上傳並部署：上傳所有檔案（含 node_modules）**。
   - ⚠️ **不要選「雲端安裝依賴」**（理由見 §7）。
3. **呼叫**：雲開發控制台 → 雲函數 → `spike-hello` → 測試，或在小程序 console 執行：
   ```js
   wx.cloud.callFunction({ name: 'spike-hello' }).then(r => console.log(r.result))
   ```
4. **檢查回傳**：以下 `checks` 必須**全部為 `true`**——
   ```json
   "checks": {
     "sharedKernelLoaded": true,
     "domainLoaded": true,
     "resultLoaded": true,
     "disputedFreezesProfitSharing": true,
     "completedAllowsProfitSharing": true
   }
   ```
   並確認 `sharedBuild.matches` 為 `true`。
5. **記錄體積**：在部署日誌或雲開發控制台查看程式碼包大小，回報是否觸及限制。
6. **對照測試（可選但建議）**：改用「雲端安裝依賴」再部署一次，確認 `@repair/*` 是否被清除。**這個結果會直接決定 P1 之後的部署 SOP。**
7. **提供環境 ID**（A10），以建立 `docs/04-環境設定.md`。

### 若步驟 2 或 4 失敗

請把**完整錯誤訊息**貼給我。最可能的三種失敗與對策已在 `docs/02-實施計畫.md` §1.5 預備（改相對路徑 require、改 `./_shared/` 目錄、只注入實際使用的套件）。這些對策**不會改變分層設計本身**。
