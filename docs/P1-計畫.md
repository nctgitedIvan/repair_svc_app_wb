## 1. P1 的目標（一句話）

**建立一個「空的但完整」的六角形骨架**：四個雲函數能部署、能通過健康檢查、有共用的入口中介層、有分層規範與機械化檢查——**但不含任何業務邏輯**。

## 3. 新增檔案

### 3.1 新增共享套件 `@repair/entrypoint-kit`（✅ **Q1 已確認採用**）

| 路徑 | 用途 |
|---|---|
| `packages/entrypoint-kit/package.json` | 新套件 |
| `packages/entrypoint-kit/authenticate.js` | 第 1 層校驗：`wxContext.OPENID` → `UserRepository.findByOpenid()` → actor |
| `packages/entrypoint-kit/validate.js` | ① 參數校驗：宣告式 schema（零依賴實作，不引入 ajv/zod） |
| `packages/entrypoint-kit/toResponse.js` | ④ 回傳統一格式；把 `Result.error.code` 轉為一致的錯誤結構 |
| `packages/entrypoint-kit/createHandler.js` | 把 ①→④ 包成一個 factory，讓入口變成「宣告」而非「樣板」 |
| `packages/entrypoint-kit/index.js` | 匯出 |

**為什麼要獨立成套件**：中介層需要 `UserRepository`（屬 `ports`），但**不屬於 `application`**（它不是 Use Case）。若塞進 `application` 會讓 application 承擔非業務職責；若複製到 4 個雲函數則會有 4 份會走鐘的副本。

**⚠️ 這會改動兩個既有檔案**：
- `scripts/sync-shared.js`：`ORDER` 加入 `entrypoint-kit`（放 `application` 之後、`adapters` 之前）
- `scripts/check-layering.js`：`ALLOWED_DEPS` 加入 `packages/entrypoint-kit`（允許依賴 `shared-kernel` + `ports`）

### 3.4 開發規範（✅ **Q2 已確認：不建 ESLint**）

**不建 `.eslintrc.js`。** 理由：架構規則已由 `check-layering.js` 機械化保證；baseline 的 `npm run lint` 本來就因缺設定檔而失敗，補一套 2019 年的 ESLint 6 設定收益低、風險高。**升級 ESLint 是獨立任務**，不混進 P1。

### 3.5 金流介面與測試替身（新增 — 對應 §0.2 的階段解鎖）

| 路徑 | 用途 |
|---|---|
| `packages/ports/SettlementGateway.js` | **只有介面**：`capabilities()`、`onPaymentSuccess()`、`settle()`、`beforeRefund()`、`refund()`、`querySettlement()` |
| `packages/adapters/inmemory/InMemorySettlementAdapter.js` | 測試替身。**P5 的所有金流 Use Case 都用它測試** |

**為什麼放 P1**：這是「P1–P5 零外部依賴」得以成立的關鍵。有了它，P5 可以在**沒有商戶號**的情況下完成 `ExecuteProfitSharing`、`ExecuteProfitSharingReturn`、`ExecuteRefund` 的邏輯與測試。P6 只需新增真實 adapter + 改 composition root。

> ⚠️ P1 **不實作** `WeChatPayApiV3Adapter`、`CloudPayProfitSharingAdapter`、`WeChatPaySettlementAdapter`、`PlatformEscrowSettlementAdapter` —— 依 `docs/01` §9.0，A1 確認前禁止。

### 3.6 存取控制模型不在 P1

`packages/domain/access/`（`docs/01` §4.7）是**業務規則**，建於 **P3（身分與權限）**，不在 P1。P1 維持「零業務邏輯」的界線。

> **但我要誠實指出一點**：你提到拆分的理由是「讓 `AddressDisclosurePolicy` 可單測」——**這個政策其實不需要地區資料**。依 `docs/01` §3.4，它只是把訂單地址截取成「區域＋街道」，不做行政區合法性驗證。
> 所以拆分的**實際收益是工具效能與可讀性**，不是該政策的可測性（它本來就可測）。
> 若你預期它需要驗證行政區合法性，那是**另一個需求**，請告知——那會讓它從純函式變成需要注入地區資料。
