## 5. 執行過程中發現並修正的問題

> 這些是 P1 的實際產出，不只是「照計畫做完」。

| # | 問題 | 性質 | 處理 |
|---|---|---|---|
| **1** | **計畫的縫隙**：T3 把 `entrypoint-kit` 加進 `ORDER`，但套件要到 T1 才建立 → T3 到 T1 之間 `sync:check` **必然失敗** | 計畫缺口 | 照你指定的順序執行，在 T3 的 commit message 明標此暫時狀態，T1 完成後立即恢復。**已於回報中主動說明** |
| **2** | 測試用 `makeHandler({ openid: undefined })` 想模擬「未登入」，卻觸發 **JS 預設參數**機制而套用了客服的 openid | 測試寫錯 | 改用 `null`，並在測試中加註解說明這個陷阱 |
| **3** | DTO 掃描器把 `platformShareCents` 一律列為「內部欄位」→ 但這是**客服** Use Case，平台抽成本來就該看到 | **工具寫錯** | 改為**依閱聽對象**（`technician` / `internal` / `customer`）決定規則。若只有一套規則，產生的偽陽性會讓這個安全測試**最後被停用** |
| **4** | `validate` 測試對 `{v: null}` 的預期與實作語意不符（實作將 `null` 視為「未提供」） | 測試寫錯 | 修正預期並補註解說明語意 |
| **5** | `InMemorySettlementAdapter` 的私有欄位宣告在 constructor 之後，且 TIMEOUT 路徑的回傳是「未 await 的 rejected promise」 | 程式碼瑕疵 | 重構：私有欄位集中宣告、改用同步 `#resolve()` 拋錯讓 async 方法自然 reject |

**注意**：問題 3、5 是我自己寫的程式碼／工具的缺陷，**不是產品邏輯的錯誤**。
問題 2、4 是我的測試寫錯。**沒有任何一項是照計畫做完才發現的架構問題**。
