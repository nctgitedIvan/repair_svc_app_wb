# SESSION HANDOFF — 維修服務平台改造

> **用途**：換 session 時，把本文件整份貼給新的 Claude 即可無縫接手。
> **維護規則**：每完成一個大階段（P0、P1、P4a…）更新一次。
> 最後更新：2026-10-16（P4a + P4b 完成）

---

## 1. 專案一句話說明

把微信開發者工具的 **TDesign 零售電商模版**，改造成**維修服務平台**（客戶／客服／師傅／管理員四角色，含微信支付服務商分帳、退款、分帳回退），後端採**六角形架構（Ports and Adapters）**跑在微信雲開發雲函數上。

### 3.2 架構關鍵決策（技術側）

| 主題 | 決策 |
|---|---|
| 語言 | **`.js` + JSDoc**，不引入 TypeScript（`// @ts-check` + `tsc --noEmit` 列為 P1 後獨立任務） |
| 共享代碼 | `packages/` 為唯一真實來源 + `sync-shared.js` **實體複製** + **雜湊雙寫守衛** |
| 部署 | **必須選「上傳所有檔案（含 node_modules）」**，不可選「雲端安裝續依賴」 |
| 測試框架 | **Node 內建 `node:test`**（零依賴、離線可跑），不用 Vitest |
| ESLint | **不建**（`npm run lint` 已移除）；架構規則由 `check-layering.js` 機械化保證 |
| 脫敏 | 由 **Port 層的角色化查詢方法**負責；adapter 可呼叫 domain 策略做投影，**不得自寫角色判斷**（CI 擋） |
| 金流 | `SettlementGateway` capability-based 介面；P1–P5 用 `InMemorySettlementAdapter`；**A1 確認前不實作真實 adapter** |

## 6. 下一步要做什麼

### 立即（P4c）

**P4c：策略與存取控制**（`docs/P4-計畫.md` §4.3／§4.4）

- 策略 7 檔：`AddressDisclosurePolicy`、`ContactMaskingPolicy`、`ContactChannelPolicy`、`ProfitSharingPolicy`、`RefundPolicy`、`AuditChain`、`ReconciliationService`
- 存取控制 11 檔：`Permission`、`RolePermissionMatrix`、`Decision`、`AccessPolicy`、`constraints/`（Ownership／State／Region／Amount／Period／SoD）、`ApprovalPolicy`
- **P4c 需先出逐檔計畫給使用者確認**（沿用 P1／P4ab 的格式）

**P4c 要落實的已定案規則**：
- SoD 只登記在 `refunds.approve_large`
- `PeriodConstraint`（財務關帳期間不得改金額）
- `AmountConstraint` 三重檢查（單筆 ≤200／當日配額／不得超過已付，**fail-closed**）
- 新增權限 `orders.void`、`orders.reverse`
- `AccessPolicy.can()` 為**純函式**，不依賴任何 Port

### 之後

`P2a（集合＋權限＋索引＋UnitOfWork＋契約測試框架）` → `P2b` → `P3` → `P5` → `P6` → `P7/P8`

### 每階段的固定流程

1. 先出**逐檔計畫**（改哪些檔／新增哪些檔／npm script／驗收標準／影響範圍／回滾）給使用者確認
2. 使用者確認後才動代碼
3. 每個 commit 完成後回報：改了什麼、跑了什麼驗證、結果
4. 階段結束跑**逐 commit 稽核**（逐一 `git checkout` + `npm run sync` + `npm run verify`）

## 10. 給接手者的三個提醒

1. **這份文件可能已過時**。若 Git 狀態與 §4 不符，以 `git log` 為準。
2. **`npm run verify` 必須隨時全綠**。它是唯一的健康指標。紅了先修，不要繼續往下做。
3. **共享碼守衛會擋你**：改了 `packages/` 之後忘記 `npm run sync`，雲函數會拒絕啟動 —— 這是**設計**，不是 bug。
