# 05 · 上雲部署手冊（repair-test → 生產）

> 適用版本：`refactor/hexagonal`，2026-10-17。
> **目前狀態：無雲環境開發模式。** 所有 CloudDB adapter 已寫好但**尚未對真實資料庫執行**；
> 四支核心雲函數已接上 **`event.action` → P3／P5 Use Case 路由**，
> 但容器仍是 InMemory（P5-5 待換 CloudDB）。
> 本手冊是「開通雲環境後照著做」的操作文件，**不是已完成驗證的紀錄**。

## 1. 環境準備

### 1.1 你需要先有

| 項目 | 說明 |
|---|---|
| 微信小程序 AppID | 已開通雲開發權限 |
| 雲開發環境 | 建議先建 **`repair-test`**，生產環境另建 |
| 微信開發者工具 | 支援雲函數上傳／雲開發 console |
| Node.js | 與雲函數執行環境相容（本專案以 Node 18+ 開發） |
| 支付商戶號 | **P6 才需要**；沒有不影響 P2／P3／P5 上雲 |

### 1.2 建立 `repair-test` 環境

1. 開發者工具 → 雲開發 → 開通 → 建立環境，名稱例如 `repair-test`。
2. 複製 **環境 ID**（形如 `repair-test-xxxxxx`）。
3. 確認 `cloudfunctions/*/index.js` 使用 `cloud.DYNAMIC_CURRENT_ENV`（目前已如此），
   不需要把環境 ID 寫進程式碼。
4. 在雲開發 console → 資料庫 → 先確認是**空的**（全新環境）。

### 1.3 本地準備

```bash
npm install
npm run sync        # 把 packages/* 複製進每個雲函數的 node_modules/@repair/*
npm run verify      # 必須全綠（目前 1369 tests）
```

> `npm run sync` 會更新每個 `cloudfunctions/*/package.json` 的 `repairSharedHash`。
> 若忘記同步，雲函數啟動時會因 `assertSharedBuild()` 失敗而拒絕運行——這是刻意的。

## 2. 部署 `setup-db`（建立 22 集合）

### 2.1 上傳

1. 開發者工具切到 **`repair-test`**。
2. 右鍵 `cloudfunctions/setup-db` → **上傳並部署**。
3. ⚠️ 選 **「上傳所有檔案」**，不要選「雲端安裝依賴」。
   共享碼在 `setup-db/node_modules/@repair/*`，只有上傳所有檔案才會帶上去。

### 2.2 先用 dryRun 驗證共享碼（P0）

在雲開發 console → 雲函數 → `setup-db` → 測試，傳入：

```json
{ "dryRun": true }
```

預期：

```json
{
  "ok": true,
  "p0": {
    "deployed": true,
    "sharedBuildMatches": true,
    "sharedCodeLoaded": true
  },
  "sharedBuild": {
    "hash": "…",
    "hashFromPackageJson": "…",
    "checks": {
      "manifestLoaded": true,
      "hashMatches": true,
      "sharedKernelLoaded": true,
      "resultLoaded": true
    }
  }
}
```

若 `sharedBuildMatches` 或 `sharedCodeLoaded` 不是 `true`：
`npm run sync` → 重新「上傳所有檔案」→ 再測。

### 2.3 正式建立集合

傳入空物件：

```json
{}
```

預期 `collections.created` 有 22 個、`failed` 為空。
再執行一次 `{}`，應全部落在 `existing`（冪等）。

### 2.4 建立索引（console 手動）

SDK **不支援建立索引**，必須在雲開發 console 手動完成。

```bash
node scripts/p2/print-index-checklist.js
```

依清單逐一建立。**不可漏掉**的唯一索引：

- `users.openid`
- `customers.user_id`
- `cs_agents.user_id`
- `technicians.user_id`
- `carts.user_id`
- `favorites (customer_id, product_id)`
- `orders.order_no`
- `payment_records.out_trade_no`
- `profit_sharing_records.out_order_no`
- `refund_records.out_refund_no`
- `work_order_tickets.order_id`
- `system_configs.key`
- `id_sequences.key`
- `audit_logs (chain_id, seq)`

### 2.5 設定權限

**22 個集合全部設為「僅管理端可讀寫」。**
這是「前端不可信」的物理保證；請逐一核對並截圖，記錄在
`docs/P2-集合與索引.md`（可自行建立核對表）。

## 3. 部署 `probe-tx`（P0 事務探針）

### 3.1 上傳與執行

1. 右鍵 `cloudfunctions/probe-tx` → **上傳並部署：上傳所有檔案**。
2. 在 console 依序執行：

| action | 預期 |
|---|---|
| `{ "action": "reset" }` | `value: 0` |
| `{ "action": "tx-write" }` | `expected: 10`、`value: 10`、`pass: true` |
| `{ "action": "tx-rollback" }` | `before === after`、`pass: true` |
| `{ "action": "inc-atomic" }` | `expected: 10`、`value: 10`、`pass: true` |
| `{ "action": "rmw-race" }` | 記錄 `value`；若 < 10，證明無事務讀-改-寫會丟更新 |

3. 把結果貼回 `docs/P2-0-事務核實報告.md` 的追加區塊。
4. **驗證完成後刪除 `probe-tx` 雲函數與 `_probe_tx` 集合。**

### 3.2 若事務不可用

`CloudDBUnitOfWork` 目前使用 `db.runTransaction`。若探針顯示事務不可用：
- 先停下來，不要繼續部署業務函數；
- 依 `docs/P2-0-文檔核實報告.md` §3.6 改成樂觀鎖＋`_.inc` 的替代方案；
- 重新跑 `npm run verify` 後再上傳。

## 4. 部署四支核心雲函數

> 四支業務 API 已接上 `event.action → UseCase` 路由（見 §4.3）。
> 不帶 `action` 的呼叫仍回傳健康檢查（`ok`／共享碼雜湊／runtime／可用 action 清單）。

### 4.1 上傳

對以下目錄，逐一右鍵 → **上傳並部署：上傳所有檔案**：

1. `cloudfunctions/customer-api`
2. `cloudfunctions/technician-api`
3. `cloudfunctions/cs-api`
4. `cloudfunctions/admin-api`
5. `cloudfunctions/payment-callback`
6. `cloudfunctions/scheduled-jobs`

> `cs-api`／`admin-api` 是 P5 路由所需；`payment-callback`／`scheduled-jobs`
> 仍是健康檢查骨架（P5-3／P5-4 待辦）。

### 4.2 健康檢查

在 console 對每支函數測試 `{}`，預期：

```json
{
  "ok": true,
  "service": "customer-api",
  "sharedBuildHash": "…",
  "runtime": { "node": "v…", "env": "repair-test-…", "hasOpenid": true }
}
```

- `hasOpenid` 在從小程序呼叫時應為 `true`；console 直接測試可能為 `false`。
- `sharedBuildHash` 必須與 `cloudfunctions/<fn>/package.json` 的 `repairSharedHash` 一致。

### 4.3 `event.action` 路由（已接上）

呼叫格式：

```js
wx.cloud.callFunction({
  name: 'customer-api',
  data: { action: 'order.pay', orderId: 'order-R20261016000001' },
});
```

路由由 `@repair/entrypoint-kit` 的 `createRouter()` 統一處理：
`action 形狀 → 身分驗證 → action 是否存在 → 參數 schema → 角色宣告 → Use Case`。
入口不含業務規則；狀態前提與資源歸屬由 `AccessPolicy`／domain 判斷。

| 函數 | actions |
|---|---|
| `customer-api` | `auth.me`、`order.create`、`order.pay`、`order.requestRefund`、`order.confirmAcceptance` |
| `technician-api` | `auth.me`、`order.accept`、`order.complete` |
| `cs-api` | `auth.me`、`order.assign`、`order.confirmCompletion`、`order.requestRefund`、`refund.approve`、`settlement.computeProfitShare` |
| `admin-api` | `auth.me`、`order.assign`、`order.confirmCompletion`、`refund.approve`、`settlement.computeProfitShare`、`settlement.execute` |

> 尚未有 Use Case、因此**刻意沒有**路由的 action：
> 查詢類（QueryMyOrders／ViewOrderDetail）、`order.cancel`、`order.reject`、
> 師傅收益查詢、後台 Manage*／Query*。
> 這些必須先寫 Use Case 再登錄路由；入口不得直接呼叫 repository。
>
> ⚠️ `admin-api` 目前仍用 OPENID 驗證；Web 後台正式啟用前必須完成 P8-2 獨立認證。

## 5. 契約測試（CloudDB）

### 5.1 現在的狀態

- `tests/contract/inmemory/**`：本機執行，已全綠。
- `tests/contract/clouddb/**`：預設 **skipped**，需要真實雲環境。
- **`contract-test-runner` 雲函數尚未建立**（P2d 待辦）。

### 5.2 上雲後的執行方式（二選一）

**(A) 建立臨時 `contract-test-runner`（建議）**
1. 新增 `cloudfunctions/contract-test-runner`，把 `tests/contract/clouddb/**` 與
   `packages/adapters/clouddb/**` 一起打包。
2. 只部署到 **`repair-test`**，**不要部署到生產**。
3. 測試資料一律用 `__test__` 前綴；跑完刪除。
4. 在 console 觸發，回傳 `pass/fail` 與失敗案例。

**(B) 在雲函數內設定 `RUN_CLOUD_CONTRACT=1`**
- 需要把 `tests/contract/**` 複製進臨時函數；
- 設定環境變數 `RUN_CLOUD_CONTRACT=1`；
- 執行後清理 `__test__` 資料。

### 5.3 驗收

- 所有契約測試（InMemory＋CloudDB）全過。
- `audit_logs` 的 `chain_id`／`(chain_id, seq)` 唯一索引存在。
- 測試資料已清理（無 `__test__` 前綴殘留）。

## 7. `bootstrap.js` 注入 CloudDB（示意）

> 目前四支 bootstrap 都使用 InMemory。以下為**未來切換模板**，
> 不要直接貼上就上線；需先確認 P2-0 探針與契約測試通過。

```js
const {
  createCloudDBClient,
  createCloudDBUnitOfWork,
  createCloudDBOrderRepository,
  createCloudDBCustomerRepository,
  createCloudDBUserRepository,
  createCloudDBProductRepository,
  createCloudDBServiceRepository,
  createCloudDBPaymentRepository,
  createCloudDBRefundRepository,
  createCloudDBProfitSharingRepository,
  createCloudDBWorkOrderRepository,
  createCloudDBWorkOrderMessageRepository,
  createCloudDBAuditLogRepository,
  createCloudDBIdSequenceRepository,
  createCloudDBSystemConfigRepository,
  createCloudDBCategoryRepository,
  createCloudDBCartRepository,
  createCloudDBFavoriteRepository,
  createCloudDBInquiryRepository,
  createCloudDBTechnicianRepository,
  createCloudDBCsAgentRepository,
  createCloudDBOrderItemRepository,
  createCloudDBOrderQueryAdapter,
} = require('@repair/adapters');

function buildContainer() {
  const cloud = require('wx-server-sdk');
  const client = createCloudDBClient(cloud);
  const uow = createCloudDBUnitOfWork(client);
  const idSequence = createCloudDBIdSequenceRepository({ client, uow });
  const clock = { now: () => Date.now() };

  const orderRepository = createCloudDBOrderRepository({ client, uow });
  const customerRepository = createCloudDBCustomerRepository({ client });
  const userRepository = createCloudDBUserRepository({ client });
  const productRepository = createCloudDBProductRepository({ client });
  const serviceRepository = createCloudDBServiceRepository({ client });
  const paymentRepository = createCloudDBPaymentRepository({ client });
  const refundRepository = createCloudDBRefundRepository({ client });
  const profitSharingRepository = createCloudDBProfitSharingRepository({ client });
  const workOrderRepository = createCloudDBWorkOrderRepository({ client });
  const workOrderMessageRepository = createCloudDBWorkOrderMessageRepository({ client });
  const auditLogRepository = createCloudDBAuditLogRepository({ client, idSequence });
  const systemConfigRepository = createCloudDBSystemConfigRepository({ client });
  const categoryRepository = createCloudDBCategoryRepository({ client });
  const cartRepository = createCloudDBCartRepository({ client });
  const favoriteRepository = createCloudDBFavoriteRepository({ client });
  const inquiryRepository = createCloudDBInquiryRepository({ client, uow });
  const technicianRepository = createCloudDBTechnicianRepository({ client });
  const csAgentRepository = createCloudDBCsAgentRepository({ client, uow });

  return {
    orderRepository,
    orderItemRepository: createCloudDBOrderItemRepository({ client }),
    customerRepository,
    userRepository,
    productRepository,
    serviceRepository,
    paymentRepository,
    refundRepository,
    profitSharingRepository,
    workOrderRepository,
    workOrderMessageRepository,
    auditLogRepository,
    idSequence,
    systemConfigRepository,
    categoryRepository,
    cartRepository,
    favoriteRepository,
    inquiryRepository,
    technicianRepository,
    csAgentRepository,
    orderQuery: createCloudDBOrderQueryAdapter({
      orderRepository,
      customerRepository,
      clock,
    }),
    clock,
  };
}
```

> ⚠️ 別忘了 `paymentGateway` 仍應注入 `MockPaymentGateway` 或 P6 的真實 adapter；
> 真實支付 adapter 只能在 A1（商戶號）確認後啟用。

## 8. 回滾與清理

| 動作 | 方式 |
|---|---|
| 回滾雲函數程式 | 開發者工具重新上傳上一版，或 `git revert` 後重新部署 |
| 回滾前端 | `config.apiMode` 改回 `'fake'` |
| 刪除臨時函數 | `probe-tx`、`setup-db`、`contract-test-runner`（驗收後） |
| 刪除測試集合 | **不要刪 22 個正式集合**；只刪 `_probe_tx` 與 `__test__` 資料 |
| 資料庫回滾 | 集合刪除不可逆；上線前先在 `repair-test` 演練 |
